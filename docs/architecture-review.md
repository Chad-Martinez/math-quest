# Scene 01–03 architecture review

This assessment describes the Scene 03 production baseline. The [architecture overview](architecture.md) covers the wider software. Each consolidation below is a proposal to review with the next relevant scene. The standards branch contains documentation and templates.

## Existing reuse and duplication

| Capability | Existing implementation and seam | Duplication or constraint |
| --- | --- | --- |
| Scene lifecycle and navigation | `chapter-ui.js` mounts scenes, tracks practice, manages crossfades and passes advancement callbacks. Missing Egg and Adventure Map expose `dispose`. | Welcome returns a stage and manages its own timer. Missing Egg owns a beat timer and CSS teardown. Map owns a travel frame loop, timer and media listener. The controller handles each shape separately. |
| Layers and responsive layouts | Welcome and Missing Egg use orientation-specific pictures, HTML dialogue and separate sprites. Map overlays controls, friends and SVG waypoints on a scale-preserving board. Missing Egg and Map already reuse parts of the Welcome control styling. | Layout is deliberately scene-specific. Some dialogue markup, DOM-building and focus work repeat. Welcome and Missing Egg need different art crops from the whole-island map. |
| Sprites, expressions and walking | Scene 01 owns the shared T-Rex walk art. Missing Egg swaps approved poses per beat. Map uses the same walking images, direction changes and route distances. | Two CSS frame sequences and one frame-loop implementation use the same four assets. Their placement, movement, timing and exit rules differ. |
| Dialogue, speech and motion | Chapter scenes already receive the shared `listen` and `stopSpeech` callbacks in `chapter-ui.js`. Optional narration is separate from answers. CSS media queries and scene-level motion checks support reduced motion. | Each story owns its approved beat UI and timing. Chapter and legacy speech have separate handlers. Some media queries and cancellation guards recur. |
| Map progression | `adventure-map-data.js` holds the approved route and dialogue. `adventure-map-state.js` derives destinations and marker states from the existing outcomes and checkpoint. `chapter-ui.js` preserves mounted work during a map visit or completed-stop practice. | The optional `mapFrom` field tracks a pending trip in the chapter save. Keep that single transition path and legacy save compatibility. |
| Math and manipulatives | `chapter.js` builds the five seeded questions and applies attempts with the shared `engine.js` validation. `chapter-models.js` uses the existing drag, number-line and balance infrastructure. `workspace-state.js` owns pure balance and part-whole calculations. | Chapter supply, footprint and sharing renderers add story-specific interactions. Legacy curriculum and chapter question shapes differ. Preserve parameters and intermediate steps across any adapter. |
| Parent Coach and movement | Legacy `coach.js` and `coach-panel.js` generate and display guides. Chapter `coach()` uses the chapter question and its fresh transfer. Chapter's `movementBody` already serves the scheduled and on-demand break. | Guide dialog and content shapes differ across releases. The break shell is shared in Chapter 1. |
| Persistence and rewards | `chapter.js` owns checkpoint normalization and awards the badge on the existing completion transition. Legacy `storage.js` owns earlier stars, usage evidence, review queues and resets. Chapter reads the older totals for display. | Chapter and legacy have intentionally separate, versioned records. Model arrangements and sketches are live workspace data. Drafts and checkpoint survive reload. |

## Incremental strategy

1. **Reuse first.** When Scene 04 is authorized, connect it to the existing chapter question, save, hint, model, Coach and reward flow. Keep the Berry Grove work reviewable on its own. A new layout can still use the established question and workspace boundaries.
2. **Unify cleanup when a new scene repeats it.** Review a small mount-and-dispose contract if the next scene adds another timer, listener or crossfade branch. Preserve focus, a single active narrator, skip behavior and one advancement under rapid input. Keep current scene composition and choreography. Use the existing Welcome, Missing Egg and Map tests as regression evidence.
3. **Share proven pieces when a second consumer needs them.** Start with the existing walk-frame paths and grounding metadata if they recur. Retain CSS where it handles stationary beat transitions and the frame loop where it follows a path. Consider a shared dialogue view or a small Coach adapter once two implementations need the same behavior. Keep state and outcome decisions in their current owners.
4. **Use approved content data directly when it fits.** Scene 03 already provides a practical example with its route data module. For a future kit, keep stable beat IDs and explicit typed fields. A small, testable copy or adapter can check asset paths, state references and math invariants and feed current controllers. Keep structured data declarative. Do not execute kit text or treat fixture answers as generated runtime values.
5. **Require evidence before expanding the refactor.** A proposal should name the duplication removed, affected scenes, how accessibility and save compatibility are preserved, and the regression checks needed. A general renderer or animation engine, new progress store, universal question schema or runtime manifest pipeline needs its own demonstrated use case and approval.
